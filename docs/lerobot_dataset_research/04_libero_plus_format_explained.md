# `lerobot/libero_plus` 格式：从 task、episode 到 frame

这篇笔记只解释一个核心问题：**一个机器人任务在数据集中究竟是怎么表示的？**

## 先给结论

你的理解大方向正确：机器人接收一句任务指令，通过两个摄像头和自身状态反复观察环境，持续产生动作，直到任务成功或达到最大步数。

但要修正三点：

1. `FPS = 20` 表示每 `1 / 20 = 0.05` 秒记录/控制一次，不是 0.04 秒。
2. 数据集中每个 frame 都配有一个 7 维动作标签；实际 VLA 部署时不一定每个 frame 都重新做一次完整大模型推理。很多 VLA 一次预测一个 action chunk，先执行其中若干步，再获取新观测并重新推理。
3. action 是 7 维，即 `action_0` 到 `action_6`。`observation.state` 才是 8 维，即 `state_0` 到 `state_7`。

## 一张图理解层级

```text
Task（任务类型）
例如：“把黑色碗放到盘子上”
│
├── Episode 0（一次完整尝试/一条演示轨迹）
│   ├── Frame 0: 两张图 + 8维state + 7维action
│   ├── Frame 1: 两张新图 + 新state + 新action
│   ├── Frame 2: 两张新图 + 新state + 新action
│   └── ... 直到成功或结束
│
├── Episode 1（相同任务的另一次尝试，初始状态/扰动可能不同）
└── Episode 2 ...
```

同一个 task 可以对应很多 episode；一个 episode 又包含很多 frame。

## 同一个任务为什么需要很多 episode

因为 task 只规定了**最终要完成什么**，没有唯一规定**这一回从什么场景开始、沿哪条路径完成**。

例如同一句任务：

```text
“把黑色碗放到盘子上”
```

不同 episode 可以有这些差异：

- 黑色碗和盘子的初始位置略有不同；
- 机械臂初始位置和姿态不同；
- 场景中干扰物体的存在和布局不同；
- 相机视角、光照、背景纹理或图像噪声不同；
- 指令语义相同，但措辞可能不同；
- 即使初始状态相近，专家实际走出的运动轨迹、速度和夹爪闭合时机也不会完全一样。

你说的“一个从左边拿、一个从右边拿”正是一种可能，但差异通常不是人为规定两套固定动作，而是连续初始状态和扰动造成了许多略有不同的合理轨迹。

### 它们确实会大差不差吗

会。同一 task 的很多 episode 在高层语义上本来就应该相似：都要接近同一个目标物体、抓取、移动并放置。

但对机器人学习来说，“大差不差”仍不等于“重复数据”：

```text
目标物体移动几厘米
→ 图像像素位置不同
→ 机械臂当前位置不同
→ 正确的 Δx/Δy/Δz 不同
→ 后续整条动作轨迹也不同
```

如果每个 task 只有一个 episode，模型很容易记住这段视频对应的固定动作序列。例如它可能学成“先向左移动 0.2，再闭合夹爪”，而不是学会“从图像中定位黑色碗，再根据当前 state 决定移动方向”。

多个 episode 的目的，是让模型从共同点中学习任务规律：

```text
相同：任务目标和成功条件
变化：初始状态、视觉条件和具体轨迹
希望模型学到：根据当前观测动态产生动作
```

### 为什么 LIBERO-plus 特别多

整个数据集平均约为：

```text
14,347 episodes / 40 tasks ≈ 每个 task 359 episodes
```

这不表示每个 task 精确有 359 条，也不表示只是把同一条标准演示重复 359 次。LIBERO-plus 的目标就是鲁棒性测试/训练，它在原始任务上系统改变七类条件：

1. 物体布局；
2. 相机视角；
3. 机器人初始状态；
4. 自然语言表述；
5. 光照；
6. 背景纹理；
7. 传感器/图像噪声。

因此同一任务会产生许多“目标相同、环境条件不同”的 episode。训练时这些变化帮助模型避免只记住某个固定画面；评测时则可以检查模型换了视角、光照或布局之后是否仍然完成任务。

### episode 越多就一定越好吗

不一定。关键是**有效多样性**：

- 如果 300 个 episode 几乎逐帧一样，新增信息很少；
- 如果变化太离谱、动作标签错误或与评测协议泄漏，也可能有害；
- 如果初始状态、视觉和合理控制轨迹确实不同，多 episode 才真正有价值。

所以研究数据时，不能只看 episode 数量，还要抽样比较同一 task 下多条 episode 的首帧、轨迹长度、最终帧和动作分布。

## `Frames / Episodes / FPS` 分别是什么意思

Hub 当前元数据为：

```text
Frames:   2,238,036
Episodes: 14,347
FPS:      20
Tasks:    40
```

### Frame

一个 frame 是某个控制时刻的一条数据记录。它不是只有一张图片，而大致是：

```python
{
    "observation.images.front": 前视相机图像,
    "observation.images.wrist": 腕部相机图像,
    "observation.state": 8维机器人状态,
    "action": 7维专家动作,
    "timestamp": 当前时间,
    "episode_index": 属于哪一个episode,
    "task_index": 属于哪一个task,
}
```

因此 2,238,036 frames 表示整个数据集共有约 224 万个控制时刻，不是 224 万个任务。

### Episode

一个 episode 是机器人从环境 reset 后开始，到完成任务或轨迹结束为止的一整段连续过程，也常叫：

- 一条 trajectory；
- 一次 rollout；
- 一条 demonstration（训练数据为专家示范时）。

为什么必须定义 episode？因为机器人控制是连续过程，不能把不同尝试的 frame 串起来。例如 episode A 最后一帧之后，绝不能把 episode B 的第一帧当成它的下一时刻。episode 边界还决定：

- 历史图像和未来 action window 在哪里停止；
- 环境什么时候 reset；
- 成功率的分母如何计算；
- 一句 task instruction 对应哪段完整轨迹。

### FPS

`FPS = 20` 表示相邻 frame 的理论时间间隔为：

```text
1 / 20 秒 = 0.05 秒 = 50 ms
```

在训练数据中，每隔约 0.05 秒有一组新观测和对应动作。

## 一个 episode 大约多少秒

根据总量计算平均值：

```text
平均 frames / episode
= 2,238,036 / 14,347
≈ 156 frames

平均时长
= 156 / 20
≈ 7.8 秒
```

所以这个数据集中，一条专家 episode **平均约 7.8 秒**。

这只是全数据集平均值，不代表每条都是 7.8 秒。简单任务可能更短，长时序任务可能明显更长。

LIBERO-plus 文档给出的评测最大步数分别是：

| Suite | 最大 steps | 按 20 FPS 换算的最长控制时间 |
|---|---:|---:|
| Spatial | 280 | 14 秒 |
| Object | 280 | 14 秒 |
| Goal | 300 | 15 秒 |
| LIBERO-90 | 400 | 20 秒 |
| Long (`libero_10`) | 520 | 26 秒 |

评测时如果提前成功，episode 会成功结束；若一直没成功，到最大步数结束并计为失败。这里的秒数是按 20 FPS 的控制步换算，不包含模型计算和环境渲染造成的真实墙钟延迟。

## 自然语言是不是在一个 episode 中不变

通常是的。

`lerobot/libero_plus` 的元数据中共有 40 个 task。每个 frame 保存 `task_index`，它指向 task 表中的一句自然语言。属于同一 episode 的 frames 通常共享同一个 task，因此在这一整段操作中，任务指令保持不变。

逻辑上可以理解为：

```text
task_index = 7
→ “把某个物体放到某个位置”
→ episode 中的所有 frame 都接受这条任务条件
```

为了节省存储，磁盘上不需要在每个 frame 里重复保存整句话；可以只保存整数 `task_index`，加载样本时再查 task 表得到自然语言。

注意：LIBERO-plus 研究语言改写扰动。具体实验协议可能在评测环境中给同一语义不同措辞；但当前数据集元数据的 `total_tasks=40` 表明其基本 task ID 数量仍是 40。做语言 OOD 时要区分“任务语义”与“指令表述”。

## 两个摄像头是不是会给很多次图片

是的。每一个 frame 都对应同一时刻的两路相机观测：

```text
observation.images.front: [256, 256, 3]
observation.images.wrist: [256, 256, 3]
```

- `front`：场景前视/第三人称相机；
- `wrist`：机械臂腕部相机；
- `[256, 256, 3]`：高、宽、RGB 三通道的存储形状；
- 加载成 PyTorch tensor 后通常变成 `[3, 256, 256]`。

平均一个 episode 有约 156 frames，所以平均会有：

```text
156 张 front 图像 + 156 张 wrist 图像
```

它们按 20 FPS 随机械臂运动不断变化。

## `observation.state` 的 8 个数是什么

当前 LeRobot 的 LIBERO processor 把机器人状态整理为：

```text
state_0, state_1, state_2 : 末端执行器位置 x, y, z
state_3, state_4, state_5 : 末端执行器姿态的 axis-angle 表示
state_6, state_7          : 夹爪两个关节的位置
```

因此你看到的 `-0.13`、`0.52` 等不是类别概率，也不是好坏分数，而是机器人当时的连续物理/几何状态值，例如位置坐标、旋转表示或夹爪关节位置。

这些值的正负和大小必须结合该维的定义、坐标系和单位理解。不能看到 `0.52` 就解释为“52%”。

为什么已有两张图片还需要 state？图片告诉模型“环境看起来怎样”，state 则精确告诉模型“机械臂现在在哪里、朝向怎样、夹爪开合怎样”。

## `action` 的 7 个数是什么

LIBERO 默认相对控制动作是：

```text
action_0, action_1, action_2 : 末端执行器位置变化 Δx, Δy, Δz
action_3, action_4, action_5 : 末端执行器旋转变化
action_6                   : 夹爪开合命令
```

也就是：

```text
3维平移 + 3维旋转 + 1维夹爪 = 7维 action
```

action 描述的是“接下来机器人应该怎么动”，state 描述的是“机器人现在是什么状态”。

你提到 `action_0` 到 `action_7`，这应该是看错了一位：Hub 的 `meta/info.json` 明确给出 action shape 为 `[7]`，字段到 `action_6` 为止。

## 是不是每 0.05 秒重新看图、推理、动作

从数据采集/控制序列角度，可以先这样理解：

```text
t=0.00: 两张图 + state → action
t=0.05: 两张新图 + 新state → 新action
t=0.10: 两张新图 + 新state → 新action
...
```

但在 VLA 实际部署时，常见的是 action chunk：

```text
获取当前观测
→ 模型一次预测未来 K 个动作
→ 执行其中 N 个动作
→ 获取新的观测
→ 再次调用模型
```

所以“控制频率 20 Hz”不等于“大模型完整推理频率一定也是 20 Hz”。例如一次预测 10 个动作并执行 10 步，理论上约每 0.5 秒重新做一次策略推理；具体取决于模型的 `chunk_size`、`n_action_steps`、异步推理和实际算力。

训练时，LeRobot 可以利用 `delta_timestamps` 从逐 frame 数据中取出未来多个 action，组成 `[T_action, 7]` 的监督目标。

## benchmark 中一次 eval 是什么

通常一次 evaluation episode 就是一次完整 rollout：

```text
环境 reset
→ 给定一条自然语言任务
→ 模型反复观察和控制
→ 成功，或达到最大 steps
→ 得到 success = 1 或 0
```

如果对某个 task 设置：

```bash
--eval.n_episodes=10
```

就表示对这个 task 做 10 次独立尝试。成功率例如：

```text
10 次中成功 8 次 → success rate = 80%
```

注意区分：

- **训练数据中的 episode**：已经录好的专家演示轨迹；
- **benchmark eval episode**：当前模型在模拟器里新运行的一次尝试。

评测不是让模型“重放训练集某个 episode 的内容”，而是把模型放回环境，在线产生自己的动作。

## 最后用一句话串起来

`lerobot/libero_plus` 有 40 种任务、14,347 条完整专家演示轨迹；每条轨迹平均约 7.8 秒，每秒记录 20 个 frame；每个 frame 包含两张相机图、8 维当前状态和 7 维下一步动作，VLA 用自然语言作为整条轨迹的任务条件，反复根据新观测产生动作，直到任务结束。
